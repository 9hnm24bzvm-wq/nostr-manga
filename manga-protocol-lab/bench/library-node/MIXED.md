# Mixed public-seam workload

`mixed.py` defaults to printing a plan. The tiny two-reader qualification passed all98 offered operations after the canonical functional gate; evidence is in results/library-node-mixed/qualification-003. It establishes valid harness/public-operation integration, not target capacity or sustainable retirement. Larger measurements require separate authorization and review.

## Demand mapping boundary (2026-10-18)

This is the original-node public-seam driver. Its retained default rates below are
synthetic controls for comparison with historical runs. They do not qualify the
integrated platform's requested 8B images, 350M page loads, 300M logical progress
saves per month or its 100TB library. `mixed-plan.json` now records those requested
volumes separately under `demand_accounting`, including exact 30-day averages,
zero default progress network writes, and unresolved optional library-sync demand.
The durable `save` lane and the public-profile `sync` lane must not be relabelled
as the integrated app's default reader progress or optional library snapshots.
The default three-read page fan-out is an experiment assumption, not an observed
route fan-out. See the [current readiness audit](../../../weebdex-platform/docs/mixed-load-readiness-20261018.md).

## Design

The default independent open-loop rates are 120 durable library saves/s, 135 pageview-equivalents × 3 API reads = 405 API reads/s, 3,087 image reads/s, one original-image read through the Rust API/s, two social writes/s, 0.1 fresh original/chapter publication/import operations/s, 0.05 profile synchronization operations/s, and 10 selective library reads/s. Image/page rates approximate the monthly arithmetic averages; the 120 durable-save rate, assumed API fan-out and auxiliary rates are independently chosen synthetic controls, not a user requirement or measured peak. All 128 readers have real library trees: 126 with 30,000 completed chapters and two with 500,000. These identities form a synthetic contention mix, not a realistic human think-time model. A seeded round-robin exercises configurable user counts uniformly, and each lane reports its actually exercised reader IDs. Lower reader counts are explicitly reported and cannot establish the 128-reader scenario.

Main image traffic goes directly to the separate managed nginx origin. The low-rate `api_image` lane goes to Rust `/originals/{hash}`. Initial corpus reads verify hashes. Timed hashing is off unless `--image-hash` is provided. The default four-image public-domain fixture is a tiny hot corpus: three retained static assets and one source image for fresh uploads. It cannot represent 100 TB or a cold-cache working set. The default skew averages about 1.18 MB/read, so 3,087 images/s offers about 3.65 GB/s (29.2 Gbit/s) on this same-host fixture. The corpus report computes exact expected bytes/s and Gbit/s for the chosen files/skew; request rate alone is insufficient. No WAN or independent network capacity follows.

`--corpus` accepts the same manifest format as `server/tests/fixtures/real-images/MANIFEST.json`: scope and images with relative file, sha256, bytes, width, height and public_domain. Files must remain inside the manifest directory. The driver validates every file hash and size; up to 10,000 input images are accepted, published in bounded 32-page chapters. All files must be real JPEGs and fit configured storage/blob limits. `--hot-fraction` and `--hot-probability` select a deterministic seeded hot/cold skew. Record the exact bytes and hot-set size in `mixed-corpus.json`; a larger supplied working set still needs explicit cache/storage interpretation.

Fresh upload operations insert a unique JPEG COM metadata segment without changing the original image stream, sign the original upload, publish a signed chapter, and import it across an approved two-node peer relationship. Acceptance also requires an exact receiver-original length/MIME/hash read. These are fresh hashes, not duplicate existing-object writes. Original and manifest bytes remain retained on both nodes during the observation. `--max-new-upload-bytes` bounds planned new retained bytes per node. Disposable fixture teardown is not evidence of online deletion/reclamation. The synchronization lane admits a distinct synthetic author, publishes metadata on the peer, runs an approved durable profile sync job, and verifies the exact imported event. It includes the admission request in its measured auxiliary cost.

`reads-and-saves` explicitly disables social/upload/sync. `all-operations` requires every configured lane to be positive and at least one actual acknowledged operation per lane, otherwise the run fails qualification.

## Bounded accounting

Independent stream deadlines are generated lazily. Scheduling does not wait for requests to complete. A configurable maximum offered-operation/log budget (default two million) rejects oversized plans before setup. Global/class pending limits, at most two queued saves per reader, a maximum lateness, and request/closing timeouts bound outstanding work. Drops distinguish scheduler lateness, global/class admission, per-reader pending limit, closed window and ambiguous reader. Errors distinguish request timeout, closing cancellation and HTTP rejection statuses such as 429/503. Pending-limit drops can be caused by slow server responses; they are not automatically generator CPU failures. When the driver cannot offer on time it records a drop and fails the no-underoffer condition, rather than quietly lowering offered rate. The library lane serializes one reader's causal head updates; different readers run concurrently. A failed/ambiguous save poisons that reader, preventing unsafe retries.

Acceptance means an exact signed durable HTTP acknowledgement for a save; complete expected size/MIME for an image (and hash if enabled); exact social/publication acknowledgement; or completed sync plus exact imported event. Queued/unacknowledged writes never count. The explicit all_scheduled_operations_acknowledged_in_window flag requires every offered operation to finish during the traffic window. Results distinguish accepted inside the traffic window from late completions and verify each last acknowledged library head afterwards. The separate library-read lane fetches and verifies a signed current head, its addressed root and up to three real chunks via /library/read for both 30k/500k readers. These are bounded selective restores, not full-tree downloads. Catalogue/discovery responses must contain the expected seeded publications; empty/wrong HTTP200 does not count. Latencies include client and scheduled-to-ack p50/p95/p99, and scheduling lateness. Rare lanes start at zero in each rate phase and round up finite-window offers; actual counts/rates are reported.

Per-second bounded-histogram and process samples cover both node trees, nginx, strfry, PostgreSQL, and generator CPU/RSS/I/O. `/proc/net/dev` is namespace-wide, never per-process attribution. Own-process CPU sampling misses short-lived processes. Separate waited-child CPU deltas recover reaped-child work (including short-lived backend commands) but overlap earlier live-child observations, so they must not be added to live-child totals. RSS sums double-count shared pages. Generator shares the node host, so contention and generator saturation must be reported. Disk snapshots separate initial fixture setup, before/after traffic and final teardown. Resource sampling continues during final head projection checks, with a separate phase label. The separate bench/operator pg_diagnostics.py CLI samples both fixture databases every two seconds, plus before traffic and after final projection verification. It uses a read-only transaction and statement/lock/connect timeouts. server-backlog.jsonl records pending import/delete counts and oldest age, removed library history beyond the five-minute grace, awaiting-projection/grace holds, queued/due blob cleanup, active reclamations and public export backlog. These are internal performance diagnostics, not functional correctness oracles. Candidate rows may still be reference/lease protected; client pending, acknowledged-head visibility, and server retirement backlog remain distinct. Disk drain/long-term growth and sustainable retirement throughput require an adequate observation window and are not proven by short runs.

## Invocation after authorization

Plan only, safe before the gate:

```sh
python3 bench/library-node/mixed.py --plan --duration 20 --scale .001 --users 2 --extreme-users 0
```

Only after the canonical gate and explicit run approval:

```sh
MIXED_FUNCTIONAL_GATE=passed MIXED_EXPECTED_NODE_SHA256=CANONICAL_GATE_HASH bash bench/library-node/mixed-fixture.sh UNIQUE_RESULT_NAME --duration 20 --scale .001 --users 2 --extreme-users 0
```

The launcher accepts MIXED_NODE_BIN, MIXED_PG_BIN_DIR, MIXED_NGINX_BIN and MIXED_STRFRY_BIN. Node defaults to CARGO_TARGET_DIR/release when selected, otherwise .build-release/release. It requires the canonical-gate-tested binary SHA256 and rejects any mismatch, without fallback. It records exact executable paths/hashes and aggregate source identity. The launcher uses existing optimized binaries, workspace-backed runtime and TMPDIR, loopback ports 58200/58201/58202 and PostgreSQL 55441. It refuses an existing result name. Run with the default origins; the direct driver can attach to other explicitly provisioned loopback fixtures. Configurable environment limits are recorded in `node-limits.json`; actual admin status is captured before/after. Source/binary hashes, PostgreSQL durability settings, generator package versions, raw request/resource JSONL and summary JSON accompany results. Credentials and databases remain in the private disposable runtime, never evidence output. Failure retains runtime for diagnosis; clean successful shutdown removes the owned runtime.

The tiny qualification covered every lane, managed nginx, signed upload proof, peer import and clean shutdown. Subsequent128-reader baseline/target/peak/soak runs remain individually reviewed; the proposed resource-bounded sequence is in results/rebuild-mixed-prep/NEXT-RUNS.md.

## Image-process sharding (prepared; application qualification pending)

The current default is `--image-workers 4` (configurable 1–8). Only managed-nginx image reads move into spawned workers. Signed saves, selective library reads, catalogue APIs, snapshot diagnostics, social, upload/import, sync and PostgreSQL diagnostics remain in the parent. Each child receives public image descriptors, not payloads or signing keys. A readiness barrier precedes one future monotonic start and common traffic/closing deadlines.

There is one canonical image schedule: global sequence j belongs to worker j modulo worker count. Plan counts and phase boundaries use that same rule. Aggregate image concurrency is divided among workers, while one nonblocking shared pending semaphore bounds parent plus children. Offers never wait for response completion. Per-worker request logs and summaries retain explicit drops, late acknowledgements and consumed bytes. Exact status, MIME and streamed length are required; timed hashing remains off by default. Missing/crashed workers, duplicate/missing/wrong-stripe sequences, inconsistent deadlines or accounting fail the merged result. Histograms merge bin counts, never percentile averages. Resource samples identify every worker by PID and start time through closing; waited-child CPU overlaps live-child observations.

Seven real multiprocessing/controlled-HTTP tests passed in 5.372 seconds: one versus four workers with a nondivisible peak schedule, shared parent/child pressure, common-window late ACKs, cancellation and reusable credits, startup pause, crash/missing offers, and invalid length/MIME/truncated responses. Raw merged percentiles are checked against observed HTTP request latency. Evidence: results/rebuild-mixed-prep/image-shard-seams.log. These tests establish harness accounting only. Rejected operations now retain their HTTP status in both lane summaries and operation records, separately from successful acknowledgements; pre-header transport failures have no fabricated HTTP status. Backend parity work requires a new optimized functional gate/hash before any sharded application qualification or capacity measurement.

Historical monthly-target-001 used the original single-parent image driver and saturated that generator near one CPU core. All started operations were acknowledged, but many offers were dropped for scheduling lateness; it establishes no server ceiling. Historical files and commands remain preserved. A one-worker rerun under the new process architecture is also a new measurement, not interchangeable with that historical implementation.

### Historical strict-only review corrections and qualification rules

This section records the earlier strict-only review before the later parity sharded runs and explicit bounded-completion amendment below. Its no-application-run statement describes that review date, not the current evidence inventory.

The shared `run_sharded_workload` orchestration is the path used by `mixed.main` and controlled HTTP tests. A concurrent liveness watcher detects unexpected child exits during parent traffic. It cancels the parent schedule, cancels/awaits pending parent requests and its monitor, terminates/reaps image children, and preserves partial/missing evidence in an invalid result. The pool is single-use: compromised credits are never reconstructed or reused. Maximum pending is an observed sample, not an atomic high-water mark.

Both request waiting and acceptance classification use the common absolute closing deadline. A successful response observed after that cutoff is retained as `acknowledged_after_closing` / `eventual_acknowledged_after_closing`, without counting toward accepted throughput or treating a known durable outcome as failed. No writes are replayed. Cancellation/timeouts still mean no verified acknowledgement, not proof of non-commit.

The actual exit gate now requires each lane's planned, offered and in-window acknowledged counts to agree, complete image-sequence integrity, no abort/operation/monitor/diagnostic failures, and exact unambiguous final heads. Eventual or after-window completions remain useful diagnostic evidence but cannot pass a target, peak or soak. Image-closing resource sampling is at most 1 Hz, independent of fast liveness polling.

Review regression evidence: `results/rebuild-mixed-prep/shard-review-red.log` captures the previous post-closing acceptance defect and absent orchestration tests. `shard-review-final.log` records 25 passing lightweight process/HTTP/driver/read/diagnostic-supervision/head-verification tests in 13.773 seconds. The occupied-credit crash test kills the image worker only after its image request reaches HTTP, proves prompt parent offer shutdown and no surviving worker/monitor, and rejects pool reuse. Orchestration tests sample actual child PIDs/start identities and separate generator groups, reject a late-completion pass and altered offered conservation, and exercise delayed-loop eventual-ACK classification. A separate cadence check is in `shard-orchestration-cadence.log`. No application workload has run with these changes.

### Explicit bounded-completion contract (2026-10-10)

This subsection preserves the original review-stage description. Its preparation-only statements predate the later named application runs; their immutable result reports are authoritative for executed qualifications.

The default remains `--qualification-contract strict-in-window`. Its historical flag and all in-window/after-window counts are retained. `--qualification-contract full-dispatch-bounded-completion` is a separately named, explicitly selected exit contract, recorded in the plan and final result. Neither contract changes scheduled rates or retries writes.

Both require exact planned/offered/started conservation, valid image stripes/workers, no drops/errors, all enabled operations, and the final exact projected/unambiguous head for every reader. Strict additionally requires every acknowledgement inside the offered-traffic window. Bounded completion instead requires every started operation acknowledged within both its absolute per-request deadline and the common finite closing deadline. `wait_for` alone is insufficient when the event loop stalls: an observed successful response after its request deadline is retained as `acknowledged_after_request_deadline` / `eventual_acknowledged_after_request_deadline`, with `durable_outcome_known`, excluded from acceptance and never replayed. The existing absolute post-closing classification remains separate.

Results always record `strict_in_window_qualification`, `full_dispatch_bounded_completion`, `qualification_contract`, and `qualification_passed`. Per-operation request-start/deadline timestamps and common monotonic/Unix traffic boundaries support independent reconstruction. The actual main requires all reader verification records. Controlled traffic-only seams may explicitly evaluate the predicate without final-head evidence; that is not a complete application qualification.

The request timeout (30s), closing timeout (60s) and maximum scheduling lateness (1s) are recorded safety bounds, not an agreed interactive latency SLO. Report observed p95/p99 and in-window rates. For a sustained-throughput experiment, declare warmup, stationary observation and drain windows before running; do not pick them after seeing the data.

The immutable `parity-target-001` run remains failed: 762 save-class pressure drops, eight other save drops, 120 catalogue429s and six upload-operation failures. Its seven image completions only0.516–1.390ms beyond60s are a finite-window boundary effect. A newly selected bounded contract would not make those substantive failures pass. No application workload has run under the new contract.

Controlled HTTP/process evidence is in `results/rebuild-mixed-prep/bounded-completion-{red,green,final}.log`. These tests exercise the actual shared orchestrator with four spawned image workers, reject pending drops/429s and missing counts, preserve a known response observed after an absolute request deadline, and continue to reject worker failure. They do not substitute for the newly gated application qualification.

Existing application profiling can be enabled without app-source edits by `MANGA_BENCH_PROFILE=1 MANGA_BENCH_PROFILE_EVERY=16`. The node emits `LIBRARY_PERF` records with Unix timestamps in `server-0.log`; the driver records exact common Unix traffic boundaries. Filter traces against that boundary, disclose sampling/overhead, and distinguish records crossing a boundary. The old `analyze_profile.py` assumes the legacy load-summary/server.log layout, so do not point it at mixed results without adapting only the analysis inputs. No stage timings were enabled in `parity-target-001`.

### Bounded dispatch tail, explicit policy version (2026-10-11)

The strict default keeps its hard start cutoff and now records `dispatch_start_policy=strict-window-start-v1`. Explicit bounded completion records `scheduled-before-end-bounded-start-v1`: an offer must be scheduled strictly before the original traffic end, may start after it only while its own scheduling lateness is no greater than the already declared `max_lateness`, and must start strictly before the common closing deadline. Both pre-queue and actual post-reader-lock dispatch apply these checks. Pending/class/reader credits, request/closing bounds, offer counts/rates and no-write-replay behavior are unchanged. No extra requests, unbounded catch-up or post-cutoff offer generation is allowed. This policy is not a latency SLO or a way to waive genuine under-offering/rejections.

Every lane reports `dispatch_timing`: actual first/last start offsets, start-to-start span, late-start count, maximum scheduling lateness among started operations and maximum start beyond the offer window. `started_after_window` is separately counted. Existing `sent_per_s` remains normalized by the planned offer-window duration; the actual span is reported alongside it rather than quietly redefining the denominator. ACK in-window/tail metrics and both acceptance booleans remain. `outstanding_at_window_end_observed_s` discloses when the post-scheduling pending snapshot was actually observed; a blocked scheduler/tail can make that observation later than the nominal boundary. It is not an exact continuously observed pending census at end.

The selected contract is explicitly passed to each image process. Merge independently reconstructs actual starts/late-start counts/timing from raw worker records, checks starts against that policy, verifies ACK ordering/absolute deadlines and rejects inconsistent/nonfinite timing evidence. Known responses are never replayed to repair a corrupt result.

Controlled tests exercise real HTTP and four spawned workers with a genuinely elapsed monotonic start, plus the actual orchestrator with ready workers paused until after the offer window. Bounded mode dispatches each originally scheduled request once within bounds; strict mode still drops it. Overstale, common-closing and occupied pending-credit cases still fail, and queued saves preserve causal ordering. Existing delayed-ACK, corrupt-output, worker-crash and HTTP-error tests remain. Red/green evidence is `results/rebuild-mixed-prep/dispatch-tail-{red,green,final}.log`. Independent review is required before application use.

Historical `parity-cataloguewaiting32-profile-001` passed the earlier explicit bounded-completion contract with all217,509 starts still before60s; no dispatch-tail amendment was involved. `parity-target-uninstrumented-001` remains FAIL for three image cutoff drops despite zero service errors and all dispatched operations acknowledged. Neither its raw result nor any earlier gate has been recomputed. The “no application workload” statements in older review sections describe their original review time.

The dispatch timing also reports `effective_dispatch_rate_per_s=(started-1)/(last-first)` for at least two distinct starts, otherwise null. This is the measured inter-start cadence over the actual first-to-last span, alongside the unchanged nominal schedule rate; it is not whole-window acknowledged throughput. The span and boundary overrun remain explicit, so a compressed late catch-up burst cannot be presented as sustained target throughput. Collection waits to the same common closing deadline used in each request's min(start+request_timeout, common_closing) bound; the worker reap allowance does not extend acceptance. A queued-reader HTTP test verifies a late start may complete before that common deadline without premature offer-end cancellation.

## Optional onset diagnostics (default off)

`--diagnostic-waits` adds separate five-second read-only observations, not target offers: main-node signed GET `/admin/status` retains only pool size/available/waiting, and the bounded PostgreSQL CLI groups current-main-database sessions by backend type/state/wait event. No query text, client address, credential or arbitrary status-body field is retained. The default CLI plan and workload are unchanged when the flag is absent.

Status has a one-second diagnostic deadline; the existing PG CLI owns its five-second process, two-second SQL and500ms lock bounds. Each observation kind is single-flight with missed intervals recorded rather than burst catch-up/retry. The actual driver-owned async context cancels and joins both observers, waiting for the bounded PG CLI to reap its child. Per-sample start/end/elapsed/lateness/phase, errors,429s, cancellation and skipped intervals are retained in `additional-diagnostics.jsonl`; `additional_diagnostics` reports joined tasks and unexpected task errors separately from the eight target-lane acceptance gates. Final experiment review must check this lifecycle evidence as well as the existing workload/guard checks. Missing observations are never zero waiting.

These samples add overhead. `/admin/status` itself uses Catalogue admission and PostgreSQL authentication/cleanup work; its successful samples are selection-biased during overload. PG snapshots see only sessions in the selected main database, not Rust's connection-pool queue, peer waits or database-null cluster processes. Five-second snapshots can miss short wait/lock bursts. Existing Drop-based1/16 stage profiling remains independently sampled, nested and outcome-free; front processing admission may precede the trace and is not reported as zero. Classify actual observations with common Unix traffic boundaries, not solely their coarse phase tag. Diagnostic metadata and worker shutdown have actual signed-HTTP, controlled CLI/PG and four-process seam tests before application use.

### Optional WAL/checkpointer comparison evidence

`MIXED_PG_MAX_WAL_MB` is a bounded integer fixture override (64–16384MB); omitted means512MB, bytewise equivalent to the former inline PostgreSQL snippet. `fixture_config.py` writes the actual snippet that `mixed-fixture.sh` appends after initdb. The approved candidate uses1024MB and no other application/database configuration change. A larger soft WAL allowance can consume more disk and increase recovery work; it does not relax fsync, synchronous_commit or the4GiB disk guard.

The already optional `--diagnostic-waits` query also returns selected actual sampler-session `current_setting` values with `pg_settings` raw value/unit/source, raw cluster-wide `pg_stat_wal` and `pg_stat_checkpointer` counters, independent reset timestamps and postmaster-start identity. The observer retains only validated allowlisted fields. Numeric deltas are emitted only between consecutive valid points with the same reset/postmaster identity, increasing sample clocks and nondecreasing counters. First samples, missing samples, resets/restarts, counter decreases or unavailable reset identity have explicit status and null deltas, never fabricated zero. Different views reset independently. Statistics can lag activity, and cluster counters include both fixture databases; session activity remains main-database only. Checkpointer write time includes pacing and is not foreground stalled time. PostgreSQL18.6 pg_stat_wal does not contain WAL write/sync latency fields; they are not invented.

The frozen512MB failure predates this metadata expansion. Its absent counters cannot be reconstructed; comparison has one application/database configuration factor plus expanded observer query fields, not a perfectly instrumentation-identical A/B. Keep old public/stage/checkpoint evidence, measure new observer cost/errors and watch through420s for a stall that merely moves later. No automatic replacement baseline or application run is authorized by these changes. A passing candidate would qualify that configuration under the declared workload, not alone establish causality.
