# Separate migration and runtime database roles

Fixes [issue #25](https://github.com/9hnm24bzvm-wq/nostr-manga/issues/25).
`serve` and `verify` perform no schema/function DDL. Never give the service login
ownership of schemas/functions/history, membership in the owner role, `CREATE`,
`TEMPORARY`, superuser, `CREATEROLE`, or `CREATEDB` privileges to make startup work.
Use a separately supplied owner DSN only for deliberate migration/preparation.
Do not store either DSN in source/config JSON or log it.

## Preparation order

1. Back up and stage the intended database. Apply original migrations with the
   existing reviewed `manga-node migrate NODE_CONFIG` owner-role workflow.
2. Run `weebdex-platform migrate` with the platform schema/function owner DSN.
   This applies unchanged historical migrations plus migration86, then prepares
   the function and policy attestation in one locked transaction. The source
   body remains generated by `manga_node::platform_bridge`, using the original
   catalogue visibility predicate. No protocol authority is copied into SQL
   migrations. Its fixed search path is `pg_catalog, public, pg_temp` and it is
   `SECURITY INVOKER`, so it does not grant original-table authority implicitly.
3. Apply/review the appropriate runtime grants below. Start the exact release's
   `verify`, then `serve`, using only its restricted runtime DSN.

`migrate` does not migrate original tables. A native-only development install
may omit step1: preparation writes the explicit `native-only` policy, which
returns true only for a NULL source event. Production still requires verified
original schema. Adding/restoring/changing the original schema requires another
owner-role platform `migrate` before runtime startup. If original verification
fails while a canonical policy is installed, runtime rejects startup rather than
continuing to expose source-linked projections. Preparation deliberately selects
native-only when the original schema does not verify; inspect the original
migration problem before choosing that reset.

Migration86 alone does not bless a function: until preparation commits its row,
both runtime actions fail. Runtime compares the expected policy version, schema
mode and SHA-256 with the attestation, plus the exact installed function body,
language, return/signature, volatility, strictness, parallel/security/planner-support attributes
and search path. Missing or mismatched state exits before listeners, importer,
storage maintenance or readiness. Repair using the correct owner release;
never rewrite historical checksums or grant runtime DDL privileges.

The policy gate is a startup/preflight check. An authorized owner can still change
schema/policy during an already-running service; require exclusive, reviewed
migration windows and restart/preflight after owner changes. This is not a
continuous defense against an administrator or compromised database owner.

## Grant contract

The database and its `public` original schema must have the expected ownership.
Use separately provisioned logins; the names below are placeholders, not automatic
account creation. The migration login must own `platform` objects and have the
original-schema SELECT needed for verification. Original and platform owners may
be the same controlled migration role, but the runtime login must be separate.
Do not transfer existing object ownership blindly.

Execute the following as the database/schema owners after both migration sets.
It grants the normal platform service application DML and function execution while
keeping the migration histories and preparation gate read-only. Granting SELECT
on the original schema supports importer/read-only protocol use; it does not
provide canonical publication write authority.

```sql
REVOKE CREATE, TEMPORARY ON DATABASE weebdex FROM PUBLIC;
GRANT CONNECT ON DATABASE weebdex TO weebdex_runtime;
REVOKE ALL ON SCHEMA public, platform FROM PUBLIC;
GRANT USAGE ON SCHEMA public, platform TO weebdex_runtime;
GRANT SELECT ON ALL TABLES IN SCHEMA public, platform TO weebdex_runtime;
DO $grants$
DECLARE relation RECORD;
BEGIN
  FOR relation IN
    SELECT n.nspname, c.relname FROM pg_class c
    JOIN pg_namespace n ON n.oid=c.relnamespace
    WHERE n.nspname='platform' AND c.relkind IN ('r','p')
      AND c.relname NOT IN ('schema_migrations','protocol_visibility_policy')
  LOOP
    EXECUTE format('GRANT INSERT, UPDATE, DELETE ON TABLE %I.%I TO weebdex_runtime',
                   relation.nspname, relation.relname);
  END LOOP;
END $grants$;
REVOKE INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
  ON platform.schema_migrations, platform.protocol_visibility_policy,
     public.schema_migrations FROM weebdex_runtime;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA platform TO weebdex_runtime;
REVOKE ALL ON ALL FUNCTIONS IN SCHEMA platform FROM PUBLIC;
GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA platform TO weebdex_runtime;
```

This is the platform application service contract, not a grant for ordinary end
users. Narrow grants further for deliberately disabled features only after
exercising their startup/maintenance paths. Review membership/inherited grants,
PUBLIC ACLs and existing database ownership: revoking a direct grant does not
remove authority inherited from another role. Reapply explicit grants after
migrations create new objects; do not default-grant DML to future policy/history
objects. Runtime must not be able to replace the visibility function, create an
object in either schema, or alter either migration history/preparation row.

A full embedded publisher additionally needs original application DML/sequence
and function execution for its configured publication, group, peer, storage and
worker operations. An original-schema owner can grant the corresponding service
contract while explicitly retaining read-only migration history:

```sql
GRANT INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO weebdex_runtime;
REVOKE INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER
  ON public.schema_migrations FROM weebdex_runtime;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO weebdex_runtime;
REVOKE ALL ON ALL FUNCTIONS IN SCHEMA public FROM PUBLIC;
GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA public TO weebdex_runtime;
```

Do not grant original schema/function ownership or CREATE. The runtime is a
trusted application service, not an ordinary user account. Publisher admission,
node/service identity and signer bindings are separately controlled original
operator provisions; startup grants cannot replace them.

The two-role runner also starts the actual integrated publisher with admitted
synthetic signer, isolated original storage, installed real projection backend
and supervised native listener. It checks genuine NIP-11 publication capability,
original startup DML (budget/instance/service-announcement/backend identity),
both listener shutdowns, immutable histories/policy and absence of simple- or
extended-protocol DDL. This is startup/grant proof, not signed1002 publication,
complete publisher-feature acceptance, production TLS/SSO or a deployment.

## Bounded public-seam acceptance

Build the actual binaries using the tracked lockfiles and Rust1.90+ before testing.
No browser/load runs or installations are performed by this runner. Provide the
prepared PostgreSQL executable directory, both newly built binary paths and the
existing reviewed strfry binary:

```sh
cargo build --locked --manifest-path weebdex-platform/backend/Cargo.toml --bin weebdex-platform
cargo build --locked --manifest-path manga-protocol-lab/server/Cargo.toml --bin manga-node
python3 weebdex-platform/scripts/test-runtime-privileges.py \
  --pg-bin /absolute/prepared/postgresql/bin \
  --platform-bin /absolute/build/weebdex-platform \
  --manga-node-bin /absolute/build/manga-node \
  --strfry-bin /absolute/prepared/strfry
```

The runner accepts no operator DSN. It creates an owned loopback-only disposable
cluster, distinct non-superuser owner/runtime logins, baseline upgrade and fresh
databases, and tests only real CLI/HTTP/PostgreSQL seams. It checks restricted
verify/serve/readiness, native HTTP writes, no startup DDL, forbidden function/
schema/history/gate mutation, missing or wrong body/version/security/mode gates,
canonical visibility/removal, preparation rollback, concurrent preparation and
migration-history drift/newer-version rejection. Raw generated logs and fixture
runtime state remain in ignored private `test-runtime`; sanitized named results
are in its summary. Cleanup observes the owned server/PostgreSQL termination.
Synthetic SQL rows test the public visibility predicate; they are not signed
publication acceptance or a substitute for the existing protocol HTTP suite.

The isolated fixture explicitly transfers its own `public` schema to its owner
login, so it does not depend on PostgreSQL15's changed public-schema ownership
convention. This affects only the newly created test databases.

The DDL-log guard can also be checked without Rust/PostgreSQL installed:

```sh
python3 weebdex-platform/scripts/test-runtime-privileges.py --check-ddl-parser
```
