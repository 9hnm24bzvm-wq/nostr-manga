# Reversible instance-account disabling

Approved policy: disable, never purge. No real account was disabled, deleted or reactivated during implementation or verification. All controls use disposable synthetic accounts.

## User-visible contract

The additive `/account/closure` screen is linked from public identity settings and the native public-profile editor. The user must explicitly select normal native-browser authority or the selected signer's explicitly bound instance account. Preview names the exact account ID, username and shared user revision. A fresh preparation is not a disable. Confirmation requires the exact phrase `DISABLE THIS ACCOUNT`, the same authority, account, revision and a one-use 10-minute random proof. Only its SHA-256 hash is stored. A proof never authenticates an account.

Native authority must be a normal browser session with an actual persisted `authenticated_at` within 10 minutes, rechecked in the transaction. API clients and password-recovery sessions cannot close accounts. Signed authority uses the existing fresh exact-byte NIP-98 request capability and original admission checks, with no cookie fallback. A selected signer is not automatically a native account.

Successful confirmation atomically marks the native user disabled, increments the user revision once, records `closed_at`, consumes all disable challenges, revokes every session/API client/native signer binding, consumes email tokens and linked flows, and inserts one lifecycle audit record. Biography/contact JSON is retained privately but never merged into the closed public tombstone. Public user ID, username, chapter/upload attribution, author records and contribution history remain. Ordinary disabled/banned accounts without this lifecycle marker do not gain public profiles.

No user/media/library/group membership/source records are erased. Original independent signer authority, original admission, original publications, source keys, peer copies, device Library and original encrypted Library are unaffected. A bound signer loses only its native instance-account binding. No automatic reactivation or purge exists.

## Routes

- Native `GET /api/account/closure/{native-user-id}`: private preview and concrete blockers.
- Native `POST /api/account/closure/prepare`: exact `expectedAccountId`, `expectedUserId`, `version`.
- Native `POST /api/account/closure/confirm`: `capture`, `confirmationId`, `confirmationToken`, `acknowledge`.
- Signed `GET /api/v1/nostr/user/{public-user-id}/closure?expectedAccountId={same-id}`.
- Signed compatibility `DELETE /api/v1/user/{public-user-id}`: **prepares only**, never purges or disables by itself. Same captured JSON fields.
- Signed `POST /api/v1/user/delete/{confirmation-id}`: same explicit confirm body. The path contains a random challenge identifier, never its secret token.

Private responses are no-store. Responses never echo passwords, sessions, API secrets or private profile JSON. The browser persists only a non-secret outcome fence, not the one-use token, password, session or private key. Web Locks prevents simultaneous confirmation dispatch from two same-origin tabs; denied storage or unavailable locking fails before sending. After uncertain network, malformed receipt or postflight actor/location change, reload cannot replay. The administrator reconciles the exact account ID and challenge ID. A successful HTTP 4xx refusal permits a new deliberate preview/preparation, never automatic retry. Clearing browser storage is not a recovery instruction.

## Concrete blockers, no silent cancellation

- Sole active group leadership: hand off to another active verified native member using group tools. Historical disabled membership is not an active alternate leader.
- Open/nonterminal upload: finish it or explicitly cancel only unstarted work through upload tools.
- Scheduled/starting/blocked intent: cancel only an unstarted schedule; started/uncertain work needs administrator reconciliation.
- Prepared/source-accepted publication or prepared source deletion: reconcile the exact durable command with the administrator. Never discard the intent/originals or resend merely to unblock closure.
- Submitted draft: resolve or withdraw it through draft review, without dropping any prepared source command.

The preview returns all blockers, never a truncated subset: at most 100 in each of the six families and 600 overall. Group and draft IDs allow 1–128 PostgreSQL Unicode characters; publication-command IDs allow 1–200. Source-request, upload and schedule IDs are exactly 10 ASCII alphanumeric characters. Kind/action/local-link fields have 25/116/16 UTF-8 byte ceilings and each known kind has its fixed safe local destination. Excessive ownership/work/credential histories or invalid fields require administrator assistance rather than an incomplete scan.

The shared native/signed core validates the **whole serialized JSON response** at no more than 512 KiB, including the envelope, before committing snapshot, blocked preparation, prepared challenge or confirmation receipt transactions. A streaming counting serializer refuses overflow without allocating a second unbounded serialization; no row or field is silently omitted. The client applies the same 600/100 count and field contract plus a 512 KiB **post-parse normalized JSON semantic budget**, including unknown envelope fields. This client check does not bound raw response allocation: signed transport separately enforces its existing streamed 1 MiB response cap, while the current native XHR transport has no raw response-allocation cap. No broad transport rewrite is part of this repair.

Read-only snapshots remain available through the positive PostgreSQL INTEGER maximum, 2147483647. Preparation and confirmation captures require a revision no greater than 2147483645: disabling advances it to at most 2147483646 and leaves one increment for audited administrator reactivation to 2147483647. The client refuses preparation of an exhausted revision before dispatch, and the shared core refuses it before challenge creation or mutation. A receipt must have exactly the captured revision plus one and cannot borrow the more permissive read-only snapshot bound. An account reactivated at 2147483647 can still be inspected, but another disable is refused, never wrapped or reset.

## Transaction/lock graph and current-account invariant

Native closure: all owned binding rows `UPDATE NOWAIT` in publisher order → closing user `UPDATE NOWAIT` → current session `SHARE NOWAIT` → led groups `UPDATE NOWAIT` in ID order → alternate active leader users `SHARE NOWAIT` in ID order → challenge → flow/session/client/email rows in per-table ID order, all `NOWAIT` → revoke/audit/disable in the same transaction.

Signed closure first uses unchanged original node/admission → binding `SHARE`/user `NO KEY UPDATE` authority gate, then the same NOWAIT upgrades. It never updates original admission and never enters an independently committed source/publication transaction. Auth flow→user inversions fail quickly on the closure's late NOWAIT flow/session locks.

All grants/new durable intents require a currently active target user `KEY SHARE NOWAIT`. This is compatible with existing signed `NO KEY UPDATE` and independent publication inserts; only exceptional closure uses stronger `UPDATE`. Thus committed unresolved commands block closure, in-flight new commands exclude closure, and a stale actor cannot insert a new command after closure commits. Do not strengthen normal signed writes to `UPDATE`: that would self-deadlock independent intent foreign-key locks.

A central membership trigger locks only the relevant old/new group rows in sorted order `NO KEY UPDATE NOWAIT` for every INSERT/UPDATE/DELETE, then requires active target authority for insertion, reassignment or promotion. Deletion/demotion of historical membership is allowed but still serialized against closure. This covers group create/update, moderation claim acceptance, promotion of an existing member and non-UI/direct core writers. Historical catalogue/protocol attribution imports are not authority grants and are not subject to that active-user predicate. Original protocol import never creates native group membership.

Closure locks an alternative leader's user row `SHARE NOWAIT` until commit (not KEY SHARE, which would allow an ordinary disabled/verified/roles update), so two last active leaders cannot both close. New membership cannot be inserted/promoted for a closing user. Group deletion/demotion cannot invalidate the chosen alternate while closure commits. No global membership-table lock exists.

## Already-admitted native mutation coverage

`closure::active_in` is the shared active-user transaction fence, not a cached SessionPrincipal. Catalogue entity/manga/relation cores, chapter/cover repository authority/mutation cores and shared catalogue audit; all community mutation/vote cores; upload begin/edit/open/attach/replace/remove/commit cores; moderation actions and announcements use it. Library list/follow/history/progress already use current active-user locks; profile/preferences/ratings already recheck disabled state under user NO KEY UPDATE. Credential issuance already revalidates the current user/session; rename/revoke require an unrevoked client row and conflict with closure's client locks/revocation.

The catalogue audit guard can reject a stale pure-DB write because its whole transaction rolls back. Nontransactional source publication is fenced **before** side effects: native manga/upload publication keeps the caller's active-user lock throughout preparation, independently durable intent and original publication; the facade receives the same transaction rather than allocating another connection. Native source deletion holds an active-user lock in its independent source transaction through actual submission. Upload originals may be received into temporary guarded storage before final transaction acquisition, but durable attachment, derivative installation/protect-commit, session state and source publication require a fresh active fence; abandoned temporaries are not published account contributions. An existing open upload itself blocks closure.

Future mutation families must either use the same transaction fence before external effects or prove equivalent fresh current-account locking. Creating a durable authority intent must use the central guard. Retained historical attribution must not be rejected just because its author later disabled their account.

## Administrator-only recovery, no new credentials

There is intentionally no public/self-service reactivation endpoint. Use only the deployment's existing authorized administrative PostgreSQL access, following the existing operator access/audit process. Do not create a new service account, password, API client or signer binding for recovery. This document is a procedure, not an instruction to execute against any real account.

1. Independently verify the requesting person's entitlement using the instance's existing administrative identity-recovery process. Record a non-secret case/reference in the operator audit system. If that process cannot establish entitlement, do not reactivate.
2. Reconcile the precise disable challenge in `platform.account_lifecycle_audit` and its confirmation row. Confirm `users.disabled=true`, `closed_at IS NOT NULL`, the exact current revision, the intended native user ID and latest `operation='disable'`. Unknown response is not permission to rerun disable.
3. In one explicit transaction, lock the exact user `FOR UPDATE NOWAIT`; verify its expected revision/closed marker again. Update only `disabled=false`, `closed_at=NULL`, `version=version+1`, `updated_at=clock_timestamp()`, conditional on the locked expected version/closed marker. Require exactly one affected row. Insert `account_lifecycle_audit(operation='reactivate', user_id, authority, old_version, new_version)` with the existing authenticated administrator identity and non-secret case reference; `confirmation_id` stays NULL. Commit only if both succeed; otherwise rollback. The new revision must equal old+1 and fit PostgreSQL INTEGER. The disable capture ceiling reserves this increment; never wrap, lower or reset a production revision to manufacture headroom.
4. Do **not** clear `revoked_at` on any session, API client or binding; do **not** reset used flows/tokens/challenges; do not restore old credentials. The user signs in through the ordinary existing native login/recovery process. Any future native signer binding or API client is a separate existing authorized provisioning action, not part of reactivation. Recheck public profile restoration deliberately because retained biography/contact becomes visible again.
5. Confirm the audit row and revision read-only, and confirm no old credential/binding became active. Reconcile the browser marker as described below. No browser button silently clears it.

### Exact browser-marker reconciliation, not blanket storage clearing

The marker key is `weebdex.account-disable.v1:{origin}:{lifecycle-id}` and stores only selected account ID, canonical lifecycle ID, captured revision, challenge ID and `unknown`/`confirmed`. The server-derived lifecycle ID is `users.account_lifecycle_id`, an immutable random UUID created with the user (or once by migration), identical for native and signed authority. Native IDs must not leak into the public contract, while preferred public aliases can change, so neither is a suitable cross-mode key. A central trigger forbids changing this UUID; retain it through reactivation, backup and restore. Only authenticated own-account closure responses expose it. Preparation and confirmation compare the captured `expectedLifecycleId` under the locked native user row; it never selects the owner or replaces native/signed authorization. Thus switching authority modes cannot bypass an unresolved marker. The selected account ID may be native or public according to the chosen authority; the administrator resolves it through the existing native/public alias mapping. A lifecycle ID is not an authority credential. Read-only inspection may occur before discovering the canonical marker, but it cannot clear protection or authorize a second confirmation.

After an audited disable **and** audited reactivation, verify the marker challenge exactly matches that user's disable audit, that its old/new revision matches the captured lifecycle, and that the current active user has the strictly newer reactivation revision. Verify the original challenge remains consumed and all old credentials remain revoked. Then, with the user's deliberate participation, remove **only that exact origin/lifecycle marker entry** in this browser's site-storage tools. Do not clear other origins, Library/device data or other account markers. Record the reconciliation in the existing operator case log. The user signs in freshly or obtains a separately authorized new binding, explicitly reloads the account and prepares a new revision/challenge. The application never automatically resets a marker from a read response.

For `unknown` with no matching committed disable audit, absence alone is not proof of failure. First quiesce/reconcile the exact request under the same binding/user NOWAIT lock graph and establish that it cannot still commit; retire the exact unused challenge under that lock, recording the outcome in the existing operator case log. Verify current user state/revision, lifecycle audit, and that no pending source work was modified. Only a conclusively noncommitted, retired challenge permits removal of that single marker. If the outcome cannot be established, retain protection and escalate through the existing operator recovery process. Never replay the old confirmation to discover its outcome.

Recovery is unavailable to someone who cannot establish entitlement with the existing administrator. This limitation is disclosed before confirmation.

## Verification qualification

Source and tests are authored separately from production operations. 32 finite client state-machine controls and 20 mounted Svelte controls pass locally without services or a browser launch. The mounted controls use the production bound-account adapter/validation with injected transport; native/public account IDs deliberately differ. They cover both-mode unknown/in-flight exclusion, distinct-account separation, service-scope drift and the operator-assisted marker-reset lifecycle. Client controls cover exact actor/revision/phrase/policy, blockers, denied storage, duplicate tab, lost/invalid receipt, late actor/location change, and no automatic replay. Actual disposable HTTP, SQL locking/rollback must pass the coordinated qualification slot before this feature is accepted. A source review or finite client pass alone is not proof of live concurrency, browser or production acceptance.


### Bounded-response and revision-headroom repair qualification

Additional source controls cover all six 100-item families, PostgreSQL-character versus UTF-8 widths, escaped JSON, total/per-family overflow, whole-envelope 512 KiB and +1 boundaries, and read-only versus mutation/receipt revision limits. Oversized confirmation receipts retain the durable unknown-outcome marker and never authorize replay. Pure Rust controls exercise the same response validator; separate synthetic native/signed HTTP boundary controls are added to the existing ignored owned-fixture suite, including exact final-revision administrator recovery without restoring old credentials.

These new controls are authored only until their coordinated qualification is recorded. No tests, build, service, browser or real account operation is implied by this source update. The existing transaction-failure fixture expectation correction (500 to the implementation's 503 unavailable mapping) is an independently reviewed prerequisite, not part of this product repair.
