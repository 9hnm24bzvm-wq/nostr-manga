# Signed directional title relations

## Native gap and shared core

Native catalogue relation POST/PUT/DELETE already persist `platform.catalog_relations`, use the genuine current account and `manga.relation.edit`/draft-owner policy, hold the owner title row, check its optimistic version and immutable pending-publication fence, and commit native audit atomically. Native create/delete may omit a version; update requires it. This change extracts the same transaction bodies into sealed-actor `relation_create_in`, `relation_update_in`, and `relation_delete_in` functions. Native wrappers retain their status/body/header behavior. No fake session, source signing capability or replacement CRUD model is introduced.

Public GET already returns genuine directional `manga_relation` UUIDs, a related manga relationship and an owner-title version. Public writes were501 or unavailable.

## Public signed commands

- POST `/api/v1/manga/{ownerUuid}/relation`: JSON `{targetManga,relation,version,expectedAccountId}`; HTTP200 entity, matching the pinned upstream create response status. The underlying native wrapper still returns201.
- PUT at the same path is an explicitly retained extension with the same JSON. It changes the kind of that existing owner/target edge; it does not move an edge to a different target. A no-op returns the unchanged owner version and creates no audit entry.
- DELETE `/api/v1/manga/{ownerUuid}/relation/{edgeUuid}`: JSON `{version,expectedAccountId}`; HTTP200 `{result,mangaId,relationId,version,nostr:{scope:"instance-local",versionScope:"owner_manga"}}`.

The required optimistic-version/account fields, signed DELETE JSON and PUT are explicit platform safety extensions, not claimed byte-for-byte upstream write parity. The create field names and HTTP200 follow the pinned5.13.1 inventory. Typed request structs reject duplicate and unknown fields; unknown query parameters, native IDs, wrong resource kinds, self edges and incomplete receipts fail closed.

All commands verify exact original NIP-98 URL/method/service/body/nonce proof before mutation. The exact typed User UUID is compared to the genuine actor in the final `bound_account_write` transaction. The owner, target and edge UUIDs resolve in that same transaction. DELETE proves that the persisted directional edge belongs to the exact owner; a target title UUID or an edge owned elsewhere is not a deletion capability. The native core owns current permissions, source visibility, row locks, owner version, mutation and audit.

Write entities use the same persisted edge identity as public GET and include `ownerMangaId`, the actual owner version, instance-local/version-scope metadata, and the actual related manga UUID. Deleting and recreating the same directional edge preserves its durable stored presentation alias. Reverse edges remain separate. Related targets must currently be public for create/update; removing a saved known edge does not require exposing a now-hidden target.

## Private drafts and UI

Signed GET `/api/v1/nostr/manga/{ownerUuid}/relations` is an explicit private editing-read extension for published and private titles. Its draft-only alias is `/api/v1/manga/draft/{ownerUuid}/relation`. Both require an empty body, exact NIP-98 URL proof, typed `expectedAccountId`, and current positive `ownerVersion`; normal native relation-edit grant/lock/draft-owner policy is checked inside the same repeatable-read transaction. Reading creates no source-signing or mutation authority and does not clear an uncertain write.

`limit` is1..32 (default32), `offset` is0..4096. Continuations require the actual64-hex `snapshot`. A lightweight ordered visible-edge scan and actual persisted count bind a deterministic SHA-256 over owner ID/version, hidden+visible count, and ordered native edge/kind/target/version tuples. Every page recomputes it, so an equal-count visibility swap or target-version change cannot silently mix pages. Response metadata includes canonical `ownerMangaId`, `ownerVersion`/`version`, `snapshot`, visible `total`, private-only `persistedTotal`, exact requested `offset`/`limit`, `nextOffset`, and typed requested/canonical identity proof.

Only the selected small page projects complete native target metadata and batched aliases. The complete serialized response retains the normal1MiB cap. If large legal metadata requires fewer rows, only a whole data prefix is returned and `nextOffset` advances by that exact prefix length; fields are never shortened. One intrinsically oversized resource fails closed. The transport retains its60s deadline and PostgreSQL its5s statement budget. The shared native create core enforces4096 persisted edges under the owner row lock, including hidden targets, before changing edge/alias/audit/version; update/removal remain available at capacity.

A separate `PublicRelationEditor` is mounted after the cover component in the dedicated signed title editor. The parent uses actual current title receipts and authoritative rereads after a successful relation mutation. Unsaved metadata, title writes, covers, disposition, pending original projection and unknown outcomes disable conflicting writes. Relation busy/pending state likewise gates title, cover and disposition commands. Read-only page reload/next/previous remain available and never clear an unknown-write fence. The UI loads one page, not4096 expanded targets, and uses actual persisted capacity rather than visible page length.

The controller captures signer generation, proved service, catalogue namespace, account and exact owner. A target alias needs an actual public title read plus typed resolver proof before canonicalization. Receipts must match the exact owner/target/edge, local scope and expected owner-version increment, including no-op semantics. Per-tab actor/service/catalogue/account/owner sessionStorage fences prevent uncertain command replay. Browser-restart durability and automatic reconciliation are not asserted.
