# Hosted sandbox-only preflight proposal

The preceding Ubuntu24.04 upload run39148301394 reached its native gate and failed at a sandbox-refusal browser launch banner. It does not identify a particular host/kernel/AppArmor cause. The supported Ubuntu22.04 standard runner is an explicit host trial, not a proven remedy.

A push to only `ci/browser-sandbox-preflight` would run the new dedicated workflow. Its exact branch cannot trigger the separate application E2E workflow. The job uses the unchanged official `.ci/browser/package-lock.json`, pinned actions/Node/Playwright1.62.1 and bundled Chromium1234; official CLI installation includes system dependencies. It requests sandboxing explicitly, passes no custom browser arguments, opens one fresh context and one literal data document, verifies fixed text, and closes under exact owned-process supervision. It uses Python3.10 standard-library supervision only, without installing the application's Python3.12 wheels.

Proposed bounds: one standard public Ubuntu22.04 job,20-minute hard cap; official browser installation step12minutes; worker90seconds plus25seconds owned cleanup with120seconds hard owner ceiling. The Actions runtime step has a separate3-minute envelope for terminal-record finalization, which does not extend browser work. One sanitized JSON at most64KiB is retained1day. No Rust, PostgreSQL, native application or frontend build, application URL, account secret, main merge or deployment is involved. Raw launch text, environment, command arguments and private runtime files are excluded from the artifact. Standard public-runner compute is free; artifact storage uses the user's allowance.

Finite source/injected-object controls do not establish browser capability. An explicit publication/run approval is required before this proposal can execute. A successful sandbox preflight would establish only that environment's browser/context/data-document/closure capability, not any application user journey or full-suite acceptance.

Only a current invocation that exclusively creates and validates new public bytes may emit the artifact SHA256 step output. Validation and upload require that exact current hash. A stale prior valid record surviving a refused invocation cannot be uploaded; valid newly created failed diagnostics remain eligible. Private-log limits are rechecked after terminal cleanup/draining.
