## R4-SEC-01 — P1: protocol cover materialization bypasses the new durable installation protocol

This is the still-open protocol-cover portion of R3-SEC-04, not a new duplicate finding against the now-patched native image path.

Evidence in the inspected file:

- `backend/src/protocol/covers.rs:23–33`: the independent `FileGuard` holds paths and a keep flag only. It holds no OS journal lease, and its destructor removes both the object and the recovery marker on ordinary failure.
- `covers.rs:185–210`: materialization creates object ancestry with ordinary `create_dir_all`, opens the final object, writes its bytes and syncs only its file contents.
- `covers.rs:211–224`: the pending intent is created only after the final object exists. Only the journal file contents are synced. There is no directory-entry durability barrier for object ancestry, final object or marker.
- `covers.rs:235–248`: object/reference insertion and SQL COMMIT proceed without the shared installation helper, a held marker lease or the matching object-key advisory lock.
- `backend/src/domains/uploads/sessions.rs:1520–1569`: reconciliation waits five minutes, acquires an OS marker lock plus advisory key lock, checks for a current media row, and unlinks bytes when that row is absent. The cover path does not participate in either active-installation exclusion.

Concrete scenarios:

1. A hard stop after opening/writing the final cover derivative and before creating its marker leaves permanent bytes with neither media row nor recovery identity. The bounded pending and raw/proxy-temporary scans cannot discover that final-object orphan. Repeated interrupted materialization can grow private disk usage.
2. A filesystem/power interruption after SQL COMMIT can retain the DB reference while the unsynced final directory entry is absent. Syncing inode contents alone does not establish durable namespace installation before the commit receipt. No particular hardware crash outcome is claimed from a source audit.
3. Materialization is suspended for more than five minutes between journal creation and insertion of its media rows. Maintenance can acquire the unlocked marker and key advisory lock, observe no committed row and remove the derivative. Resumed materialization can then commit a reference to a missing file. The configured short SQL statement/lock deadlines do not prevent suspension before the transaction starts.

Owner: catalogue/storage plus protocol-cover materialization. Required source acceptance: use a shared key-only prewrite intent and live OS lease before final installation, sync newly created ancestry and final entries before any reference COMMIT, retain an intent across cancelled/uncertain writes, coordinate the DB key lock, and durably clear intent after acknowledged persistence. All cover variants must follow this contract. The current native helper is an available reference implementation; an independent lookalike must establish the same invariants.

Required later genuine acceptance: interrupt materialization at prewrite/final-create/marker/SQL-commit boundaries on the same private volume, restart, preserve all current references and reclaim only unreferenced recoverable bytes. Hold a real cover installation past the cleanup eligibility age and prove maintenance cannot remove it. Verify failed unlink retries and directory durability faults without asserting that ordinary cancellation proves power-loss safety.

## R4-SEC-02 — P2: restricted recovery identities still reveal saved reading status and private reply votes

Evidence:

- `backend/src/domains/auth/principal.rs:168–222` intentionally returns a `recovery_session` from optional identity resolution because password-settings flows need it. `require_principal` at `principal.rs:256–270`, `require_browser_session` at `principal.rs:65–72` and `require_library_read` at `principal.rs:76–87` refuse that identity for their ordinary protected capabilities.
- `backend/src/domains/community/mod.rs:191–196,207–211` filters the optional viewer only on `!is_api_client`, then supplies the user's ID to the public reply list/detail DTO function. It never excludes `recovery_session`.
- `backend/migrations/0081_community_visibility.sql:38–44` returns `relationships.vote_state` from the private per-user vote row when the supplied viewer matches.
- `backend/src/domains/catalog/read.rs:104–107,240–250` obtains optional identity for `reading_status` searches, top feeds and random results. `backend/src/domains/catalog/query.rs:297–302` checks only that an identity exists, then filters the user's saved library follows/status selections. It does not require the existing owner-library capability.
- `backend/src/domains/auth/README.md:66`, ordinary direct private-list checks in `backend/src/domains/library/lists.rs:83–86,190–200`, and the recovery rejection in `principal.rs` establish the intended restricted recovery boundary.

Concrete scenario: redeem a genuine recovery email, retain the resulting purpose=`recovery` cookie, and make GET requests before changing the password. `/api/thread/<id>/replies` and `/api/thread/<id>/replies/<reply>` expose this account's private vote state. `/api/manga?reading_status=<state>` and `/api/manga/random?reading_status=<state>` reveal which public titles occur in that account's saved reading-state buckets, despite direct library routes correctly refusing recovery. These are account-specific projections, not ordinary public information.

Owner: catalogue/auth/community integration. Required source acceptance: allow ordinary public reads while refusing account-specific recovery projections; use `require_library_read` before applying reading-status filters and only a full browser-session capability for viewer-specific social state. Do not globally remove optional recovery identity in a way that breaks the deliberately restricted password-reset flow.

Required later genuine Router/DB acceptance: use a real recovery-purpose cookie with existing saved statuses and votes. Direct library and private social endpoints must refuse it; public reply list/detail must omit private vote state; every normal/top/random reading-status variant must refuse private filtering. Complete password reset, obtain the resulting ordinary session and prove the intended owner projections work. Retain issued-bearer scope/revocation and expected-account mismatch checks, including optional reads.

## R4-SEC-03 — P2: original projection subprocess outlives the owned worker's reported termination

Evidence from the independently verified 22-file freeze:

- `../manga-protocol-lab/server/src/node.rs:1013–1031` drains finite operations, then calls `shutdown`/`stop_workers(true)` for infrastructure. `node.rs:975–983` includes `backend_projection` in that final abort batch. `node.rs:990–1007` observes the parent Tokio task's termination, and `node.rs:1031` counts registered async/blocking terminal leases.
- Original `server/src/backend.rs:129–145` directly spawns GNU `timeout`, `flock` and strfry. It has no cancellation-surviving command owner, terminal operation lease or verified process-group join. `backend.rs:167` directly awaits the child as part of `tokio::join!`. Dropping the Tokio command future does not itself terminate the spawned child under its default drop behavior.
- `backend.rs:265–282` uses that command for real projection import/delete, and `backend.rs:381–402` runs it directly in the registered projector's session. Unlike scoped storage forks, this subprocess is not independently accounted for after its awaiting background parent is aborted.

Concrete scenario: the registered projector is inside a real strfry import/delete command when embedded shutdown reaches the infrastructure stop. Abort drops the parent and its command future; the registry observes a terminal parent and the finite/infrastructure lease counters can reach zero. The GNU timeout/flock/strfry group can remain alive until its separate configured timeout and kill-after period, continuing to use/write the original projection volume after native completion is reported. The bounded external timeout limits how long it survives; it does not establish that the native completion boundary waited for its termination.

The bridge owner confirmed there is no upstream wrapper preventing this path. The parent explicitly authorized a narrow `backend.rs` command-ownership fix as the 23rd original source file. That fix is pending a new freeze and fresh independent review, not approved here.

Required source acceptance: the spawned command and its full process-group completion remain terminally owned after caller/worker cancellation. Preserve existing input/output/error bounds, projection locking and original command timeout. Wait actual command termination before successful cleanup; if a longer original command timeout exceeds the embedded phase, fail truthfully. Killing only the `timeout` parent without establishing descendant termination is insufficient.

Required later genuine acceptance: hold an actual original projection command after spawn, abort its registered parent during shutdown and verify shutdown remains pending or reports unconfirmed completion until the process group actually terminates. Confirm no remaining projection child writes the volume after a successful stop, and preserve ordinary standalone projection behavior. The scoped synthetic Tokio-child tests alone cannot establish external-process ownership.
